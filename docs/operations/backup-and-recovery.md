# پشتیبان‌گیری و بازیابی

Last Updated: 2026-07-15

## وضعیت فعلی

پایگاه داده فعلی SQLite است. این انتخاب برای توسعه سریع مناسب است، اما برای تولید، همزمانی، backup، بازیابی نقطه‌ای و audit قابل اتکا کافی نیست. برای تولید، مهاجرت به PostgreSQL پیشنهاد می‌شود.

## داده‌های حیاتی

| داده | اهمیت |
|---|---|
| برگ‌های بدهی نهایی‌شده | بسیار بالا |
| برگ‌های اجرا | بسیار بالا |
| تاریخچه وضعیت و audit | بسیار بالا |
| کاربران و سازمان‌ها | بالا |
| مجوزها و mapping نقش/گروه | بالا |
| ruleها | بالا |
| fake integration requestها | متوسط تا بالا، بسته به محیط |

## سیاست پیشنهادی backup

| محیط | فرکانس | نگهداری |
|---|---|---|
| توسعه | روزانه یا دستی | کوتاه‌مدت |
| تست | روزانه | 7 تا 14 روز |
| تولید | ساعتی + روزانه | حداقل 30 تا 90 روز |

## Recovery Point Objective

برای داده‌های مالی و فرایندی، از دست رفتن داده باید نزدیک به صفر باشد. در تولید، استفاده از PostgreSQL با WAL archiving یا replication توصیه می‌شود.

## Recovery Time Objective

سامانه باید برنامه مشخص بازیابی داشته باشد:

1. تشخیص خرابی.
2. توقف سرویس‌های درگیر.
3. بازیابی پایگاه داده.
4. بررسی سازگاری Camunda process instances.
5. اجرای smoke test.
6. بازگرداندن سرویس.

## Camunda و بازیابی

Camunda state مستقل از دیتابیس برنامه است. در بازیابی، باید این دو هماهنگ باشند:

- وضعیت برگ اجرا در دیتابیس برنامه.
- وضعیت process instance و user task در Camunda.

اگر یکی از این دو عقب‌تر باشد، ممکن است برگ اجرا در دیتابیس وجود داشته باشد اما task متناظر در Camunda پیدا نشود، یا برعکس.

## Keycloak و بازیابی

Keycloak منبع احراز هویت است. backup Keycloak باید شامل realm، client، role، group و user باشد. پروفایل محلی کاربر در برنامه جایگزین Keycloak نیست.

## سناریوهای بازیابی

| سناریو | اقدام |
|---|---|
| حذف اشتباه user profile | بازیابی از backup یا audit، سپس sync با Keycloak |
| خرابی SQLite | توقف برنامه، جایگزینی فایل backup، بررسی integrity |
| خرابی PostgreSQL آینده | restore از backup و WAL |
| خرابی Camunda | restore state Camunda یا rebuild محدود با بررسی فرایندها |
| خرابی Keycloak | restore realm و کاربران، سپس اجرای sync |

## پیشنهاد مهم

قبل از ورود به تولید:

- SQLite با PostgreSQL جایگزین شود.
- Flyway یا Liquibase اضافه شود.
- backup و restore در محیط staging تمرین شود.
- هر deploy شامل migration plan و rollback plan باشد.
