# آزمون واقعی API و فرایند EF03

از ریشه پروژه اجرا کنید:

```bash
bash scripts/test-ef03-pipeline.sh 1
```

برای ارسال همهٔ ۱۰۰۰ برگه:

```bash
bash scripts/test-ef03-pipeline.sh 1000
```

این آزمون به Camunda واقعی با تنظیمات اتصال همین پروژه نیاز دارد. هر اجرا یک نمونهٔ
جدا از برنامه روی پورت آزاد localhost، یک دیتابیس SQLite جدید، کاربر
`ef03-test-sender` با رمز تصادفی و فقط مجوز `DEBT_PAPER_PUSH` و AccessID تصادفی
می‌سازد. ساخت دستی حساب یا تنظیم متغیرهای احراز هویت لازم نیست. حساب از سازوکار
Basic Authentication موجود برنامه استفاده می‌کند و حساب مدیریتی Keycloak نیست.

XML فایل `docs/paper-types-examples/ef03.ods` عیناً ارسال می‌شود. فقط پوشش JSON
تکمیل می‌شود: زمان ارسال و hash محاسبه می‌شوند؛ سال، اداره و مبلغ از XML می‌آیند؛
دورهٔ پوشش ۱ و منبع مالیاتی TAXB است. دادهٔ ناقص داخل XML اصلاح نمی‌شود.

اطلاعات پایهٔ اداره‌ها و فعالیت‌ها از فایل در دیتابیس آزمایش ایجاد می‌شوند.
داده‌های مؤدی، بدهی و برگ اجرا فقط از مسیر HTTP و worker واقعی ایجاد می‌شوند.
تعارض کد رهگیری با TIN، تخصیص TIN دوم به یک شخص در مدل فعلی و تعلق یک برگ بدهی
به مؤدی دیگر، پیش از آغاز فرایند با خطای مشخص ثبت می‌شوند. آزمون برای عبور دادن
این ردیف‌ها نه XML را تغییر می‌دهد و نه محدودیت‌های دیتابیس را حذف می‌کند.
نسخه‌ای از BPMN فعلی با شناسه و نوع job منحصربه‌فرد هر اجرا روی Camunda منتشر
می‌شود. workerهای عادی در نمونهٔ آزمایشی خاموش‌اند؛ فقط سه worker اختصاصی این
آزمون فعال می‌شوند، بنابراین برنامهٔ اصلی jobهای آزمایش را دریافت نمی‌کند.

آزمون ابتدا رد درخواست بدون رمز (401) و AccessID اشتباه (403) را بررسی می‌کند.
سپس برگه‌ها را به `/api/v1/debt-papers/push` می‌فرستد و منتظر پاسخ فرایند می‌ماند.
برای پاسخ موفق، XML ذخیره‌شده، شناسهٔ فرایند، روابط مؤدی و بدهی، مبالغ با دقت
اعشاری، وضعیت و تاریخچه‌ها کنترل می‌شوند. یک ارسال تکراری باید 409 برگرداند و
برگ جدید نسازد. در پایان، یک قاعدهٔ محدودکننده فقط در دیتابیس آزمایش ایجاد می‌شود
و رد صدور واقعی توسط Camunda با پاسخ 422 نیز آزموده می‌شود.
خطاهای اعتبارسنجی منبع در گزارش می‌مانند. خطای زیرساخت یا نتیجهٔ
نامشخص باعث توقف تست می‌شود؛ ارسال خودکار مجدد انجام نمی‌شود.

مسیر هر اجرا با `EF03_RUN_DIRECTORY` چاپ می‌شود و داخل `.local/ef03-tests/` است:

- `test.sqlite`: دیتابیس ماندگار آزمایش برای بررسی بعدی.
- `run.json`: شناسهٔ فرایند Camunda، پورت و مشخصات اجرای تست.
- `results.jsonl`: نتیجهٔ هر درخواست، trace ID، شناسهٔ برگ و شناسهٔ instance.
- `summary.json`: خلاصهٔ اجرای کامل و کنترل‌های انجام‌شده.
- `credentials.json`: اطلاعات حساب همان اجرا، با دسترسی فقط برای مالک فایل.

لاگ اجرای دستور نیز در `.local/ef03-tests/logs/` ذخیره می‌شود.

برای پایش آخرین اجرا، حتی هنگام ارسال داده‌ها:

```bash
python3 scripts/monitor-ef03-test.py
watch -n 2 python3 scripts/monitor-ef03-test.py
```

در Camunda نیز با شناسهٔ فرایند داخل `run.json` جست‌وجو کنید. متغیرهای `referenceID`
و `apiGatewayTraceID` ارتباط هر instance با درخواست API را مشخص می‌کنند.
پس از پایان تست، برنامه و workerهای آزمایشی بسته می‌شوند؛ دیتابیس، گزارش‌ها و
سوابق اجرای Camunda باقی می‌مانند. اجرای بعدی کاملاً مستقل است.

این تست فقط با `-Def03.live=true` اجرا می‌شود و جزو اجرای عادی تست‌های واحد نیست.
