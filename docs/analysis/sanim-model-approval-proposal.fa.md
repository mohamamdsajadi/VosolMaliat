# پیشنهاد مدل و نگاشت سنیم برای تأیید

وضعیت: پیشنهاد به تأیید کاربر رسیده و پیاده‌سازی در شاخه `feat/sanim-execution-document-model` انجام شده است. جزئیات، محدودیت‌ها و نتیجه آزمون‌ها در [گزارش پیاده‌سازی](sanim-model-implementation.fa.md) آمده است؛ پایگاه داده عملیاتی تغییر داده نشده است.
مبنا: پاسخ‌های کاربر، all_sanim_fields.ods، XML for Arrears.xlsx و مدل فعلی برنامه.

## تصمیم‌های ثبت‌شده

- XML اصلی کامل و بدون تبدیل، در همان ستون xmlPayload نگهداری می‌شود؛ جدول ردیف مالی نداریم.
- هفت مبلغ مستقل لازم است: مانده بدهی، مالیات، عوارض، جرایم، پرداختی، اعتبار و بخشودگی. واحد پول ویژگی جداگانه است.
- مبالغ اولیه سند حفظ می‌شوند؛ پاسخ‌های استعلام تاریخچه دارند و مبالغ جاری را به‌روزرسانی می‌کنند.
- مانده EF03 فعلاً HB است؛ نگاشت NB اکسل برای این مبلغ اعمال نمی‌شود.
- تگ مالی ناموجود فعلاً صفر است؛ مقدار غیرعددی یا مبهم، «ناموجود» محسوب نمی‌شود.
- دریافت ناقص یا متعارض ثبت می‌شود، اما ایجاد پرونده قابل پردازش و شروع گردش‌کار متوقف می‌ماند. نقص هویت باید پیش از ادامه تعیین تکلیف شود.
- واحد مالیاتی پیش‌شرط دریافت نیست. کد اداره سنیم مرجع خارجی سامانه است و با PK داخلی یکسان فرض نمی‌شود. حذف جدول tax_unit یا وابستگی‌های سایر بخش‌ها فعلاً پیشنهاد نمی‌شود.
- reference تکراری به فراخواننده خطا می‌دهد، حتی اگر XML یکسان باشد؛ پاسخ پیشنهادی HTTP 409 است.
- announcementType الزامی است؛ پنج قالب با نگاشت مستقل پشتیبانی می‌شوند.
- واحد ریال، مقادیر اعشاری و منفی دقیق و بدون گردکردن/تغییر علامت حفظ می‌شوند.
- اختلاف هویتی/مالی پوشش پیام و XML ثبت و پیش از ادامه بررسی می‌شود؛ هیچ‌کدام بی‌صدا جایگزین دیگری نمی‌شود.

## مدل با کمترین تغییر

| موجودیت موجود | اصلاح پیشنهادی |
|---|---|
| DebtPaperPushRecord | حفظ XML و پوشش پیام؛ افزودن نوع قالب، نسخه نگاشت و وضعیت/دلیل نیاز به بررسی. ثبت مستقل از موفقیت نگاشت و گردش‌کار. |
| FinalizedDebtPaper | توسعه به نقش منطقی SanimExecutionDocument بدون الزام تغییر نام جدول؛ مشخصات واقعی شماره/تاریخ سند، مؤدی، کد اداره سنیم، مستند صدور و هفت مبلغ اولیه. |
| DebtInformation | هفت مبلغ تجمیعی جاری با نوع دقیق؛ در آغاز برابر مبالغ سند و سپس از استعلام معتبر به‌روزرسانی شوند. ستون‌های قدیمی تا اصلاح مصرف‌کنندگان حفظ شوند. |
| DebtInquiryResult | حفظ تاریخچه پاسخ؛ نگهداری زمان مؤثر پاسخ و نسخه نگاشت. مبالغ تجمیعی استخراج‌شده در تاریخچه نیز برای گزارش قابل ثبت‌اند. |
| ExecutionPaper | حفظ نقش پرونده داخلی و روابط؛ ایجاد/ادامه پس از تعیین تکلیف هویت، اعتبار داده و الزامات عملیاتی. |
| Taxpayer / اشخاص / سازمان | حفظ روابط معتبر؛ اطلاعات اولیه سند از اطلاعات جاری مرجع تفکیک شود؛ کد سنیم مستقل از شناسه داخلی باشد. |

هفت ویژگی مشترک مبالغ اولیه و جاری:
`outstandingDebtAmount`, `totalTaxAmount`, `totalDutyAmount`, `totalPenaltyAmount`, `totalPaidAmount`, `totalCreditAmount`, `totalRemissionAmount`.
نوع Java: BigDecimal؛ نوع ذخیره‌سازی باید دقیق و سازگار با SQLite باشد. مقیاس و حدود ذخیره باید قبل از migration مشخص شوند؛ تبدیل به Long یا Double و گردکردن خودکار مجاز نیست.

## قواعد نگاشت پیشنهادی

این جدول‌ها پیشنهاد استخراج نرم‌افزاری از عنوان فیلدها هستند، نه فرمول مالی یا حقوقی مصوب. مانده از تگ/فرمول مخصوص قالب می‌آید و با یک فرمول عمومی دوباره ساخته نمی‌شود.
تگ‌های ناموجود صفرند. مقادیر منفی بدون abs/max نگهداری می‌شوند. مجموع‌های آماده دوباره با جزئیات تشکیل‌دهنده‌شان جمع نمی‌شوند.

### EF03 و EF104

| مبلغ | EF03 | EF104 |
|---|---|---|
| مانده بدهی | HB | RB |
| مالیات | CB | 0 |
| عوارض | 0 | 0 |
| جرایم | GB | PB |
| پرداختی | EB | XB |
| اعتبار | 0 | 0 |
| بخشودگی | DB، با قید اینکه معافیت و بخشودگی ترکیبی است | QB |

صفر در جدول یعنی در این نگاشت، مؤلفه مستقلی برای استخراج تعریف نشده؛ اثبات صفر اقتصادی نیست. این موضوع در metadata نگاشت ثبت شود. در EF03 ستون بخشودگی با وضعیت COMBINED_EXEMPTION_REMISSION معرفی می‌شود؛ تفکیک این دو از داده ممکن نیست.

### EF23 و EF23_1

نماد W.QD، W.RD و W.SD فقط به تگ مربوط به بخش پسماند اشاره می‌کند؛ W تگ واقعی XML نیست.

| مبلغ | پیشنهاد |
|---|---|
| مانده بدهی | LC + MC + BD + CD + JD + W.SD |
| مالیات | NB + RC |
| عوارض | OB + SC + ED + W.QD |
| جرایم | DC + EC + FC + GC + TC + UC + VC + WC + FD + GD + HD |
| پرداختی | JC + KC + ZC + AD + ID + W.RD |
| اعتبار | XB + YB + BC + CC |
| بخشودگی | 0؛ تگ تجمیعی صریح معرفی نشده |

اعتبار در این پیشنهاد شامل جمع اعتبار خرید قابل کسر و اعتبار انتقالی است؛ پرداخت‌های بدهی فقط در totalPaidAmount قرار می‌گیرند. این تعریف نیازمند تأیید کارفرماست. XB/YB با اجزای PB/QB/... دوباره جمع نمی‌شوند. عنوان مالیات در این دو قالب بر پایه جمع فروش قبل از کسر اعتبار است؛ مانده مستقل از فرمول اکسل خوانده می‌شود.

GE مقدار قابل پرداخت/انتقال است و با مالیات ناخالص فروش NB هم‌معنا نیست. پیشنهاد بالا «مقدار گزارش‌شده قالب» را نگه می‌دارد؛ گزارش بین‌قالبی باید مبنای NET_REPORTED را لحاظ کند. از GE منفی، اعتبار مثبتِ جداگانه تولید نمی‌کنیم؛ علامت اصلی حفظ می‌شود. اگر جمع ناخالص مالیات یا تفکیک مالیات/عوارض داخل GE لازم باشد، داده فعلی برای آن کافی نیست. این بخش نیازمند تأیید صریح است.

## تکرار تگ‌ها

تکرارهای صرفاً نمایشی بدون مانع ذخیره می‌شوند؛ نیازی به استخراج همه جزئیات نداریم. اما SD در فرمول مانده و QD/RD در پیشنهاد عوارض/پرداختی استفاده می‌شوند. اگر تشخیص بخش پسماند از نمونه واقعی ممکن نباشد، انتخاب اولین/آخرین یا جمع همه تکرارها مجاز نیست؛ نتیجه همان مبلغ نیازمند بررسی است. این محدودیت فقط درباره تگ مصرف‌شده در محاسبه است.

## دریافت و استعلام

۱. اعتبارسنجی پوشش پیام و نوع قالب؛ دریافت تکراری → خطا.
۲. ثبت پایدار XML و فراداده؛ سپس نگاشت مشترک و مالی.
۳. هویت ناقص یا تعارض مهم → پاسخ خطا با شناسه پیگیری، وضعیت NEEDS_REVIEW، بدون ادامه گردش‌کار. رکورد خام برای تعیین تکلیف باقی می‌ماند.
۴. داده معتبر → ثبت/اتصال هویت، سند اولیه، مبالغ جاری و پرونده.
۵. استعلام معتبر → ثبت تاریخچه و به‌روزرسانی مبالغ جاری در یک تراکنش؛ اصل XML و مبالغ اولیه ثابت بمانند.
۶. پاسخ تکراری استعلام دوباره اعمال نشود؛ پاسخ قدیمی‌تر، وضعیت جدیدتر را بازنویسی نکند. معیار زمان مؤثر پاسخ با قرارداد استعلام تعیین شود.
۷. قاعده صفر برای تگ ناموجود مربوط به XML اولیه است. اگر استعلام، پاسخ جزئی باشد، نبود یک مبلغ نباید خودکار آن را صفر کند؛ قرارداد کامل/جزئی بودن پاسخ باید مشخص شود.
